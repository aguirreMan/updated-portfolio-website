<CaseStudySection
  id="streaming-ai"
  title="Streaming AI responses"
  date="Updated September 23, 2026"
>
Streaming has two responsibilities: sending tokens to the browser immediately while simultaneously building a complete AI response that can be persisted once generation finishes.

```ts
  for (const line of lines) {
    if (!line.startsWith('data:')) continue
    const jsonData = line.slice(5).trim()
    if (jsonData === '[DONE]') break
    try {
      const parseData = JSON.parse(jsonData)
      const content = parseData.choices[0]?.delta?.content
      if (content) {
        fullMessageContent += content
        controller.enqueue(encoder.encode(`data: ${JSON.stringify({ content })}\n\n`))
      }
    } catch (error) {
      console.error('Streaming parse Error happened ', error)
    }
  }
```

Rather than treating the response as a single payload, the application buffers incoming data, decodes it into text, and processes complete Server-Sent Events before forwarding each token to the client. This creates a responsive chat experience while the AI is still generating its answer.

One architectural decision I made was delaying persistence until the stream successfully completed. Although users receive tokens immediately, I avoid writing partial responses to the database.

```ts
async flush() {
  if (fullMessageContent.trim()) {
    await saveChatMessage(
      conversationId,
      'assistant',
      fullMessageContent
    )
  }
}
```

Waiting until the stream finishes keeps conversation history consistent, reduces unnecessary database writes, and prevents incomplete AI responses from being stored if a request is cancelled midway through.

While this code works this code here 
```ts 
const parseData = JSON.parse(jsonData)
const content = parseData.choices[0]?.delta?.content
```

is not type-safe because ```ts JSON.parse()```
returns a type any 
which meant the parsed AI response could be accessed without TypeScript verifying its structure. 
The code compiled, but there was no guarantee that the external response actually matched the shape the application expected.

I changed the runtime value to type unknown forcing the response to prove its shape before the application could access it.

```ts
const parseData: unknown = JSON.parse(jsonData)

if (!streamingChunkValidation(parseData)) continue

const content = parseData.choices[0]?.delta?.content

```

The application expects each streaming event to match this structure
 
 ```ts

export interface StreamingChunk {
  choices: Array<{
    delta?: {
      content?: string
    }
  }>
}
```

But the external response now has to satisfy that contract before the streaming logic uses it.

```ts
function streamingChunkValidation(value: unknown): value is StreamingChunk {
  if (typeof value !== 'object' || value === null) return false
  if (!('choices' in value)) return false

  const choices = value.choices

  if (!Array.isArray(choices)) return false

  // validate each streaming choice...
}
```
This moved the streaming route from trusting the provider response to validating data at the boundary before it enters the application.
</CaseStudySection>

<CaseStudySection
  id="canceling-requests"
  title="Propagating cancellation end-to-end"
  date="Updated August 11, 2026"
>

Stopping the client from reading a streamed response isn't enough. The server can continue waiting on the AI model while the model generates tokens the user will never receive.

```ts
abortController.current?.abort()
abortController.current = new AbortController()

const response = await fetch('/api/openrouter', {
  method: 'POST',
  signal: abortController.current.signal,
})

```


The client cancelling a request is only half of the solution. The server also needs to stop processing the request; otherwise the AI model continues generating tokens that will never be displayed, while still consuming API credits.

```ts
const response = await fetch(
  'https://openrouter.ai/api/v1/chat/completions',
  {
    method: 'POST',
    signal: request.signal,
    // ...
  }
)
```

By forwarding the client's abort signal to OpenRouter, the entire request lifecycle stays synchronized. When the user cancels a request, the browser stops listening, the server stops waiting, and the AI provider stops generating tokens.

</CaseStudySection>

<CaseStudySection
  id="rate-limiting"
  title="Rate limiting AI requests"
  date="Updated August 11, 2026"
>

Unlike a typical API endpoint, every request sent to `/api/openrouter` has a direct cost attached to it. Every prompt generates tokens, every token consumes API credits, and without safeguards a single user, buggy retry loop, or malicious script could generate thousands of expensive requests in seconds.

Rather than treating rate limiting as an afterthought, I made it one of the first steps in the request pipeline. Requests are authenticated first, then checked against a per-user rate limit before any communication with OpenRouter begins.

```ts
const { userId } = await auth()

if (!userId) {
  return new Response(
    JSON.stringify({ error: 'Unauthorized user' }),
    { status: 401 }
  )
}

const { success } =
  await chatGenerationRateLimiting.limit(userId)

if (!success) {
  return new Response(
    JSON.stringify({ error: 'Rate limit exceeded' }),
    { status: 429 }
  )
}
```

The order is intentional. Authentication establishes the identity of the caller, allowing requests to be limited per user instead of per IP address. Once a request belongs to a verified user, it can be evaluated against that user's quota before any AI generation begins.

This means requests that fail either check never reach OpenRouter. No model is loaded, no tokens are generated, and no API credits are consumed. The cheapest AI request is the one that never has to execute.


Rate limiting is enforced entirely on the server, so the client cannot bypass the quota or initiate AI generation before the request is validated.

</CaseStudySection>


<CaseStudySection
  id="state-architecture"
  title="Centralizing coordinated state transitions"
  date="Updated August 11, 2026"
>

The first version of Gorilla AI managed conversations, message history, loading state, and the active chat through separate `useState` hooks.

The problem wasn't the number of state values. It was that they represented parts of the same workflow, and one user action could require several updates to stay synchronized.

```ts
const [isLoading, setIsLoading] = useState(false)
const [conversations, setConversations] = useState<Conversation[]>([])
const [conversationStore, setConversationStore] = useState<ConversationStore>({})
const [activeConversationId, setActiveConversationId] = useState<string | null>(null)
```

Deleting a conversation made that coupling visible.

```ts
function handleDeleteConversation(id: string) {
  setConversations((previous) =>
    previous.filter((conversation) => conversation.id !== id)
  )

  setConversationStore((previous) => {
    const next = { ...previous }
    delete next[id]
    return next
  })

  if (activeConversationId === id) {
    setActiveConversationId(null)
  }
}
```

A single delete required three coordinated updates: removing the conversation, deleting its message history, and clearing the active selection when necessary. Each setter was individually correct, but nothing guaranteed the complete transition happened as one operation.

As the chat workflow grew, I moved these coordinated transitions into a reducer so related state changes could be handled as a single operation.


The previous delete workflow can now be represented as a single dispatch:

```ts
dispatch({
  type: 'DELETE_CHAT',
  payload: id,
})
```

The reducer owns the complete transition:

```ts
case 'DELETE_CHAT': {
  const nextStore = { ...state.conversationStore }
  delete nextStore[action.payload]

  return {
    ...state,
    conversations: state.conversations.filter(
      (conversation) => conversation.id !== action.payload
    ),
    conversationStore: nextStore,
    selectedChat:
      state.selectedChat === action.payload
        ? null
        : state.selectedChat,
  }
}
```

Components now describe what happened, while the reducer owns the complete state transition.

The refactor did not make the chat workflow less complex. It made that complexity explicit and gave related state transitions one predictable place to live.

</CaseStudySection>

<CaseStudySection
  id="refining-chat-architecture"
  title="Refining the chat architecture"
  date="Updated September 15, 2026"
>
The reducer solved the coordination problem, but centralizing the chat workflow exposed a different issue: it was now managing both client-owned interactions and data loaded from the server.
 
```ts
export type ChatActions =
  | { type: 'SELECT_CHAT'; payload: string }
  | { type: 'STREAM_MESSAGE'; payload: { id: string; content: string } }
  | { type: 'DESELECT_CHAT' }
  | { type: 'SET_LOADING_CONVERSATIONS'; payload: boolean }
  | { type: 'SET_LOADING_MESSAGES'; payload: boolean }
  | { type: 'LOAD_CONVERSATIONS'; payload: Conversation[] }
  | { type: 'LOAD_MESSAGES'; payload: { id: string; messages: Message[] } }
```
 
The reducer wasn't only coordinating client transitions anymore. `LOAD` and `SET_LOADING` actions were also making it responsible for the lifecycle of database-backed data. That responsibility propagated through Context — a component that only needed `deselectChat` still consumed the same chat context that exposed messages, loading state, and streaming state.
 
```ts
const { deselectChat } = useChatContext()
 
<Link href="/dashboard" onClick={deselectChat}>
  Gorilla AI
</Link>
```
 
I started by moving conversations and their loading lifecycle out of the reducer entirely, into TanStack Query:
 
```ts
const { data, isLoading, error } = useQuery({
  queryKey: ['conversations'],
  queryFn: async () => {
    const response = await fetch('/api/conversations')
  },

```

That migration exposed a routing problem. Conversation navigation moved to `/dashboard/[chatId]`, but the rest of the application still determined the active conversation from `selectedChat` in the reducer — two sources of truth that could silently diverge:
 
```text
URL       /dashboard/abc123
Reducer   selectedChat = abc123
```
 
Rather than synchronizing them, I removed the duplicate state. The URL is now the single source of truth for which conversation is active:
 
```ts
const params = useParams<{ chatId?: string }>()
const activeConversationId = params.chatId ?? null
 
function handleConversationSelect(chatId: string) {
  router.push(`/dashboard/${chatId}`)
  onClose()

```
 
This also clarified what each route means:
 
```text
/dashboard             → new conversation
/dashboard/[chatId]    → persisted conversation
```
 
Moving to file-based routing surfaced a layout problem, too. I introduced a nested dashboard layout so the shell persists across both routes, while each route owns only its own presentation:
 
```text
app/(dashboard)/dashboard/
├── layout.tsx
├── page.tsx
└── [chatId]/
    └── page.tsx
```
 
**Reducing the reducer to temporary message state**
 
With conversation identity in the URL and conversations in TanStack Query, I kept shrinking the reducer's responsibilities. Persisted messages are now fetched through a query keyed by conversation ID:
 
```ts
const {
  messages: fetchedMessages,
  isLoading,
  error,
} = useFetchMessages(chatId)
```
 
The reducer no longer owns fetched message history. It represents only messages that temporarily exist on the client while a response is being generated:
 
```ts
export type ChatActions =
  | { type: 'ADD_USER_MESSAGE'; payload: { message: string } }
  | { type: 'ADD_ASSISTANT_MESSAGE' }
  | { type: 'APPEND_STREAM_CONTENT'; payload: { content: string } }
  | { type: 'REMOVE_EMPTY_ASSISTANT_MESSAGE' }
  | { type: 'RESET_PENDING_MESSAGES' }
```
 
The UI combines authoritative server history with temporary streaming state:
 
```ts
const displayMessages = [
  ...fetchedMessages,
  ...pendingMessages,
]
```
 
This gives each piece of state one clear owner:
 
```text
TanStack Query   → persisted conversations and messages
URL              → active conversation identity
Reducer          → temporary pending messages
useChat(chatId)  → coordinates the active conversation lifecycle
```
 
When generation completes, the messages query is invalidated so TanStack Query can fetch the persisted server version before the temporary messages are discarded:
 
```ts
await queryClient.invalidateQueries({
  queryKey: ['messages', chatId],
})
 
dispatch({
  type: 'RESET_PENDING_MESSAGES',
})
```
 
That handoff exposed one more edge case: for a brief window, the freshly fetched messages and the pending messages can represent the same data — the assistant's just-completed reply exists in both the server response and the local stream buffer simultaneously. Invalidating the query before clearing pending prevents the UI from falling back to stale history while the refetch is running, but it does not make the handoff atomic. There can still be a brief render where the same messages exist in both collections.
 
Rather than assuming two independently updated arrays will reconcile themselves, I'm treating that transition as an explicit synchronization problem. The next stage of the refactor is to give temporary streaming state a clearer identity and lifecycle so it can be replaced cleanly once the persisted server version becomes authoritative.
 
**Separating the persistent shell from conversation behavior**
 
Earlier versions of the dashboard layout instantiated the main chat hook itself and passed messages, streaming state, and callbacks down through the shell. As the state boundaries above became clearer, that responsibility moved downward. The shared layout now owns only persistent presentation:
 
```text
DashboardLayout
├── Sidebar
└── children
```
 
And the persisted conversation route owns its own conversation-specific behavior:
 
```ts
const { chatId } = useParams<{ chatId: string }>()
 
const {
  messages,
  isLoading,
  sendMessage,
  isStreaming,
  stopStreaming,
} = useChat(chatId)
```
 
The route is now responsible for interpreting `chatId`; `useChat` coordinates everything that follows from it.
 
**Designing the first-message lifecycle**
 
The next architectural problem appeared while redesigning `/dashboard` itself. I wanted a new conversation to behave like a modern chat interface: navigating to "New Chat" shouldn't immediately create an empty database record. The conversation should begin only when the user submits the first message.
 
```text
/dashboard
    ↓
user submits first message
    ↓
server creates conversation
    ↓
conversation receives an ID
    ↓
generation begins
    ↓
/dashboard/[chatId]
```
 
I started separating conversation creation from AI generation. A dedicated conversations endpoint can create the persisted conversation and return its server-generated ID. `/api/openrouter` now verifies that the supplied conversation exists and belongs to the authenticated user before beginning generation.
 
```text
POST /api/conversations
→ create persisted conversation
→ return conversation ID
 
POST /api/openrouter
→ verify conversation ownership
→ generate response
→ persist messages
```
 
This moves the architecture toward a clearer server boundary: the client can request a new conversation, but the server determines which persisted conversation exists and verifies ownership before allowing AI generation. There is still some cleanup remaining in this boundary — the generation route currently retains older conversation-persistence behavior from the previous architecture, so conversation creation and conversation metadata updates aren't completely separated yet.
 
It also revealed a React lifecycle problem: `/dashboard` and `/dashboard/[chatId]` are different page components, so navigating after the first message unmounts the landing page while the AI response may still be streaming. If the reducer, `AbortController`, and streaming state are owned by that page, their React owner disappears mid-transition.
 
The dashboard layout survives navigation between both child routes, which gives that temporary state a natural lifetime boundary. The architecture I'm currently building toward:
 
```text
DashboardLayout
│
└── ChatSessionProvider
    │
    ├── active streaming chatId
    ├── pending messages
    ├── streaming status
    └── AbortController
    │
    ├── Sidebar
    │
    └── children
        ├── /dashboard              → new-chat presentation
        └── /dashboard/[chatId]     → persisted-chat presentation
```
 
Importantly, this doesn't move server state back into Context. TanStack Query keeps owning persisted conversations and messages — the provider would own only ephemeral state whose lifetime needs to survive the route transition. Tagging that state with its conversation ID also prevents an active stream from leaking into the wrong conversation if the user navigates away mid-generation:
 
```ts
const pendingForCurrentChat =
  session.chatId === chatId
    ? session.pendingMessages
    : []
```
 
This stage changed how I think about state ownership. The question isn't only whether state belongs to the client or the server — it's how long that state needs to live. Persisted data belongs to the server cache. Route identity belongs to the URL. Temporary streaming data belongs to the client, but its owner has to survive whatever route transitions happen while generation is still in flight.
 
*Currently in progress: defining the smallest possible `ChatSessionProvider` contract before moving the existing streaming lifecycle out of `useChat`.*

<CaseStudySection
id="synchronizing-persisted-messages"
title="Synchronizing streamed and persisted messages"
date="Updated September 23, 2026"
>


After moving persisted message history into TanStack Query the reducer was responsible only for temporary messages created while a response was being generated.

```ts
const { messages: fetchedMessages } = useFetchMessages(chatId)

const [pendingMessages, dispatch] = useReducer(chatReducer, [])

const displayMessages = [
  ...fetchedMessages,
  ...pendingMessages,
]
```
This separation gave persisted and temporary state clear owners, but it introduced a synchronization problem when generation finished.

While a response was streaming, pendingMessages contained the user's newest message and the assistant response. The server eventually persisted both messages to the database, but the TanStack Query cache did not automatically know that the API route had changed the underlying data.

Clearing the temporary messages before synchronizing the query could therefore make the newest messages disappear from the interface:

fetchedMessages  → previously persisted history
pendingMessages  → new user + assistant messages

generation finishes
        
server persists new messages
        
RESET_PENDING_MESSAGES
        
pendingMessages = []
        
TanStack Query still contains stale history
        
refresh required to see the latest messages

The database was correct, but the client had removed the temporary copy of the new messages before its cached server state had been synchronized.

Instead of clearing pending state immediately, I made the transition back to server-owned state explicit. A small synchronization hook invalidates the messages query for the active conversation:
```ts
export function useSyncMessages() {
  const query = useQueryClient()

  async function syncMessages(chatId: string) {
    await query.invalidateQueries({
      queryKey: ['messages', chatId],
    })
  }

  return { syncMessages }
}
```
useChat now waits for that synchronization before discarding its temporary messages:
```ts
finally {
  setStreaming(false)

  await syncMessages(chatId)

  dispatch({
    type: 'RESET_PENDING_MESSAGES',
  })
}
```

The intended handoff now has an explicit order:

Reducer owns temporary streaming messages
         
server persists messages
        
TanStack Query synchronizes
        
reducer clears temporary state
        
TanStack Query resumes ownership of persisted history

Making this synchronization explicit prevents useChat from intentionally clearing its temporary state before asking TanStack Query to refresh the persisted history.

The handoff, however, is still not atomic. fetchedMessages and pendingMessages remain independently managed collections. During synchronization, the newly persisted messages can briefly exist in both, creating the possibility of duplicate messages during the transition.

Rather than treating that as the same problem, I am treating it as the next stage of the synchronization work: temporary messages need a clearer identity and lifecycle so the persisted server version can replace them cleanly.

As useChat became more focused on coordinating the message lifecycle, I also moved the lower-level stream parsing into readStream, keeping the hook responsible for orchestration rather than the mechanics of decoding SSE events.
