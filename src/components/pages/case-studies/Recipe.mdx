<CaseStudySection
  id="ingredient-data"
  title="Modeling ingredient data"
  date="updated August 12, 2026"
>

The math behind ingredient scaling was straightforward. The harder problem was that the ingredient data wasn't modeled for calculations.

My original implementation extracted ingredient amounts from formatted strings using split() and parseFloat(). While this worked, the logic depended on the exact format of the API response and became increasingly fragile as the application evolved.

```tsx
const parts = currentDataString
  .split(':')[1]
  .trim()
  .split(' ')

const originalAmount = parseFloat(parts[0])
```

Ingredient scaling wasn't really a string parsing problem it was a data modeling problem.


Instead of treating ingredient measurements as formatted strings, I modeled them as explicit TypeScript objects.

```tsx
export interface MeasureUnit {
  amount: number
  unitShort: string
}
```

The scaling logic then became straightforward arithmetic.

```tsx
const scaledAmountUS = ingredient.measures.us.amount * scaleFormula
```
Once ingredient measurements became explicit numeric values, scaling no longer depended on parsing presentation-formatted strings.

</CaseStudySection>

<CaseStudySection
  id="transforming-data"
  title="Transforming 3rd party data"
  date="updated August 12, 2026"
>
The Spoonacular API returns significantly more data than the frontend actually needs. Passing the raw response directly into React would have tightly coupled the UI to a third-party API contract and scattered transformation logic throughout the application.

Instead, I introduced an Express backend that acts as the boundary between Spoonacular and the frontend. Rather than functioning solely as a proxy, the server transforms API responses into a shape the UI expects before they're returned to React.

Instructions are reduced to the fields the UI needs rather than exposing Spoonacular's complete instruction structure.

```tsx
  const steps: SpoonacularInstruction[] = instructionInformation[0].steps.map((step) => ({
    number: step.number,
    step: step.step
  }))
```

Ingredients require a different transformation because the application needs both the original numeric measurements for scaling and formatted values for display.
```tsx
function formatIngredients(ingredients: Ingredient[]) {
  return ingredients.map((ingredient) => ({
    name: ingredient.name,
    nameClean: ingredient.nameClean,
    amount: ingredient.amount,
    original: ingredient.original,
    unit: ingredient.unit,
    measures: ingredient.measures,
    formattedMeasures: formatMeasurements(ingredient),
  }))
}
```

Numeric measurements remain available to the scaling logic, while formatted US and metric values are derived for presentation.

```tsx
  function formatMeasurements(ingredient: Ingredient): FormattedMeasures {
    const us = ingredient.measures?.us
    const metric = ingredient.measures?.metric
    return {
      us: us ? `${us.amount} ${us.unitShort}` : '',
      metric: metric ? `${metric.amount} ${metric.unitShort}` : '',
    }
  }
```

The transformed pieces are assembled into the recipe shape that is cached and returned to the frontend.

```tsx
const recipeCachedData = {
  id: ingredientInformation.id,
  title: ingredientInformation.title,
  image: ingredientInformation.image,
  servings,
  instructions: steps,
  extendedIngredients: ingredientsArray,
}

saveRecipe(id, recipeCachedData)
res.json(recipeCachedData)
```

</CaseStudySection>

<CaseStudySection
  id="sql-caching"
  title="Reducing Third-Party API Requests"
  date="updated August 12, 2026"
>

Spoonacular's free tier limits the number of API requests that can be made each day. During development, repeatedly opening the same recipe while refining the UI quickly consumed that quota, even though the underlying recipe data rarely changed.

Rather than requesting the same recipes multiple times, I introduced a lightweight SQLite cache in the Express backend. The first request stores the recipe locally, and subsequent requests are served from the cache instead of calling the Spoonacular API again.

```tsx
const cachedRecipe = getRecipe(id)

if (cachedRecipe) {
  return res.json(cachedRecipe.recipe)
}
```

Then after the cache miss, the recipe is fetched from the Spoonacular API and stored in the cache for future requests.

```tsx
const [instructionData, ingredientData] = await Promise.all([
  fetchWithTimeout(instructionsWithKey, {}, 15000),
  fetchWithTimeout(ingredientsWithKey, {}, 15000),
])
```

After the data is then transformed into the desired format and stored in the cache, the recipe is returned to the client.

```tsx
saveRecipe(id, recipeCachedData)
res.json(recipeCachedData)
```

The cache intentionally avoids expiration and invalidation logic. For this application, recipe data changes infrequently, so keeping the implementation simple provided the biggest benefit without introducing unnecessary complexity.

</CaseStudySection>

<CaseStudySection
  id="paginated-server-state"
  title="Simplifying Paginated Server State"
  date="updated August 12, 2026"
>
The original recipe search hook managed the entire request lifecycle itself: loading state, cancellation, accumulated results, and pagination all lived inside React state and effects.

```tsx
const [recipes, setRecipes] = useState<SpoonacularResultsComplexSearch[]>([]) 
const [totalResults, setTotalResults] = useState(0) 
const [isLoading, setIsLoading] = useState(false)

const controller = new AbortController()

fetchRecipes(query, page, random, controller.signal) 
  .then((response) => { 
    setTotalResults(response.totalResults) 
    setRecipes((prev) => page === 1 ? response.results : [...prev, ...response.results]) 
  })
```

This worked, but it meant the hook was manually coordinating state that ultimately came from the server. I migrated the search flow to TanStack Query's useInfiniteQuery, letting the query cache own the request lifecycle
while keeping the pagination rule explicit.

```tsx
queryFn: ({ pageParam = 1, signal }) => 
  fetchRecipes(query, pageParam, random, signal), 
getNextPageParam: (lastPage, allPages) => { 
  const loadedRecipes = allPages.reduce( 
    (total, page) => total + (page.results?.length ?? 0), 0 ) 
  return loadedRecipes < lastPage.totalResults ? allPages.length + 1 : undefined 
}
```

Spoonacular returns totalResults, so pagination stops when the number of accumulated recipes reaches that value.

I added hook level tests around the pagination boundary: the first page should expose another page, while the final accumulated result should stop further pagination.

```tsx

expect(result.current.recipes).toEqual(page1Mock.results)
expect(result.current.hasNextPage).toBe(true)

result.current.fetchNextPage()

await waitFor(() =>
  expect(result.current.isFetchingNextPage).toBe(false)
)

expect(result.current.recipes).toEqual([
  ...page1Mock.results,
  ...page2Mock.results,
])

```

```tsx
expect(result.current.hasNextPage).toBe(false)
```

<CaseStudySection
   id="testing-ingredient-scaling"
   title="Testing ingredient scaling behavior"
   date="August 12, 2026"
>
As ingredient scaling became more structured, I added tests around the behaviors most likely to produce incorrect recipe data. Incrementing and resetting the serving count were straightforward to verify, but the more important cases involved keeping multiple measurement systems synchronized and handling incomplete ingredient data.

The application allows users to switch between US and metric measurements. Scaling therefore can't update only the measurement currently displayed in the UI. Both representations need to be recalculated from the same serving ratio so switching units doesn't reveal stale values.

```tsx
const scaleFormula = servingsSize / initialServings 

const scaledAmountUS = ingredient.measures.us.amount * scaleFormula 
const scaledAmountMetric = ingredient.measures.metric.amount * scaleFormula

```

I test both values after changing the serving size. For a recipe with 2 US cups and 240 metric units at 4 servings, increasing the recipe to 5 servings produces a scale factor of 1.25. Both representations should reflect that same change.

```tsx

act(() => {
  result.current.incrementServings() 
}) 

const scaledIngredient = result.current.scaleIngredients[0] 

expect(scaledIngredient.measures?.us.amount).toBe(2.5) 
expect(scaledIngredient.measures?.metric.amount).toBe(300) 
expect(scaledIngredient.formattedMeasures?.us).toContain('2.5')

```

Third-party ingredient data also isn't always complete. When an ingredient doesn't contain the measurements required for scaling, the hook preserves the original ingredient rather than attempting to calculate from missing values.

```tsx
const { result } = renderHook(() => 
  useScaleServings(4, ingredientWithoutMeasures)
)

expect(result.current.scaleIngredients[0]).toEqual(ingredientWithoutMeasures[0])
```
These tests focus on the behavior behind the feature rather than the serving controls themselves: changing serving size must keep both unit systems synchronized, while incomplete API data must remain usable without producing invalid measurements.
