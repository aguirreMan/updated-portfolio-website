<CaseStudySection
  id="overview"
  title="Overview"
>

Recipe applications seem straightforward until they rely on live, third-party data. Search, ingredient scaling, nested API responses, request limits, and inconsistent data structures quickly introduce challenges beyond simply displaying recipes.

I built this full-stack application with React, TypeScript, Express, and the Spoonacular API to explore those problems. The architecture includes backend data transformation, SQLite caching, typed API contracts, and reusable frontend logic designed to make recipe discovery and serving adjustments more reliable and maintainable.

<CaseStudySection
  id="ingredient-data"
  title="Modeling ingredient data"
>

Ingredient scaling became one of the more interesting engineering problems in the application. While the math itself was straightforward, the ingredient data returned by Spoonacular wasn't designed around scaling calculations.

My original implementation extracted ingredient amounts from formatted strings using split() and parseFloat(). While this worked, the logic depended on the exact format of the API response and became increasingly fragile as the application evolved.

```tsx title="Original implementation"
const parts = currentDataString
  .split(':')[1]
  .trim()
  .split(' ')

const originalAmount = parseFloat(parts[0])
```

As I continued working on the project, I realized ingredient scaling wasn't really a string parsing problem it was a data modeling problem.


Instead of treating ingredient measurements as formatted strings, I modeled them as explicit TypeScript objects.

```tsx title="MeasureUnit.ts"
export interface MeasureUnit {
  amount: number
  unitShort: string
}
```

The scaling logic then became straightforward arithmetic.

```tsx title="scaleServings.ts"
const scaledAmountUS =
  ingredient.measures.us.amount * scaleFormula
```

Once ingredient measurements became explicit numeric values, the scaling algorithm no longer depended on parsing formatted strings. The logic became easier to understand, simpler to test, and more resilient to changes in the API response.

</CaseStudySection>

<CaseStudySection
  id="transforming-data"
  title="Transforming 3rd party data"
>
The Spoonacular API returns significantly more data than the frontend actually needs. Passing the raw response directly into React would have tightly coupled the UI to a third-party API contract and scattered transformation logic throughout the application.

Instead, I introduced an Express backend that acts as the boundary between Spoonacular and the frontend. Rather than functioning solely as a proxy, the server transforms API responses into a shape the UI expects before they're returned to React.

Centralizing that transformation reduced duplication in the frontend and made it easier to evolve the UI without depending on the exact structure of Spoonacular's responses.

</CaseStudySection>

<CaseStudySection
  id="sql-caching"
  title="Reducing Third-Party API Requests"
>

Spoonacular's free tier limits the number of API requests that can be made each day. During development, repeatedly opening the same recipe while refining the UI quickly consumed that quota, even though the underlying recipe data rarely changed.

Rather than requesting the same recipes multiple times, I introduced a lightweight SQLite cache in the Express backend. The first request stores the recipe locally, and subsequent requests are served from the cache instead of calling the Spoonacular API again.

The cache intentionally avoids expiration and invalidation logic. For this application, recipe data changes infrequently, so keeping the implementation simple provided the biggest benefit without introducing unnecessary complexity.

</CaseStudySection>
